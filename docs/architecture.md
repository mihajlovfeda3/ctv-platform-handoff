# Архитектура первой итерации

## Границы

Одно модульное приложение: Next.js App Router, React, TypeScript, Tailwind CSS, Route Handlers, PostgreSQL 17, Drizzle ORM, Zod. Отдельного микросервисного бэкенда нет. Общая платформа не привязана к NIS: организации и контекст оценок представлены данными.

Запрос браузера → Server Component или Route Handler → серверный сервис → Drizzle → PostgreSQL. Клиентская оболочка отвечает только за навигацию. Импорты БД и серверных сервисов помечены `server-only`, так что клиентский компонент не может включить их в браузерный bundle.

## Модули

- `domain/scenario.ts`: независимые диапазоны показателей, входной контракт сценария, параметры каталога.
- `server/scenarios.ts`: создание, список, детализация, справочники, связанные объекты.
- `features/import`: адаптеры CSV/JSON, явное сопоставление колонок, нормализация и диагностика без БД.
- `server/import.ts`: атомарная запись проверенного пакета с сохранением исходных ID и raw-строк.
- `server/seed.ts` и `scripts/synthetic.ts`: согласованный, повторяемый синтетический набор.
- `db/schema.ts`, `db/migrations`: схема и версионированные миграции, включая защиту от циклов бизнес-иерархии.

## Чтение и фильтры

Список фильтруется SQL-запросом, а не массивом в браузере. Поиск по названию, описанию и исходному ID экранирует SQL wildcard-символы. Значения передаются параметрами. Фильтр направления проходит все три уровня технологий через `EXISTS`, поэтому несколько методов не дублируют сценарии в выдаче. Параметры валидируются Zod. Размер страницы по умолчанию 12, максимум 100, порядок устойчивый: исходный ID и UUID. Count и список читаются в одной `repeatable read` транзакции.

Оценки каталога выбираются только из явно указанного организационного контекста (`synthetic-lab` по умолчанию) и только с `isCurrent=true`. В карточке доступны все контексты и история. Значения разных организаций не объединяются. Вычисляемых показателей нет.

## API

| GET                          | Ответ                                                    |
| ---------------------------- | -------------------------------------------------------- |
| `/api/scenarios`             | `items`, `total`, `page`, `pageSize`, `pages`, `context` |
| `/api/scenarios/:id`         | Сценарий, бизнес-контекст, источник и оценки             |
| `/api/scenarios/:id/related` | Технологии, задачи, эффекты, кейсы, решения, проекты     |
| `/api/references`            | Направления, технологии, методы, бизнес-узлы и группы    |

Фильтры: `q`, `directionId`, `businessNodeId`, `functionalGroupId`, `implementation=yes|no|unknown`, `maturity=1..5`, `readiness=1..7`, `impact=1..3`, `context`, `page`, `pageSize`. UI предоставляет основные фильтры; остальные доступны API и URL.

Ошибки: 400 для параметров, 404 для отсутствующей записи, 503 при недоступной БД. API возвращает `Cache-Control: no-store` и не раскрывает SQL, параметры подключения или исходные импортируемые строки. Публичных изменяющих HTTP-обработчиков нет. Внутреннее создание использует Zod и ограничения БД.

## UX

Пять постоянных разделов, компактные горизонтальные фильтры, широкая рабочая область. Состояние поиска хранится в URL. Нативная GET-форма работает без клиентской загрузки всего набора. Полная карточка имеет самостоятельный адрес и стандартную навигацию браузера. В первой версии это проще и доступнее, чем выдвижной инспектор; инспектор можно добавить в ТЗ №2.

Каталог реализован первым рабочим представлением. Подложка будущего радара сохраняет голубые сектора, концентрические уровни и сине-оранжевую легенду, но не содержит фиктивных данных. Остальные модули описывают свою готовность без имитации аналитики. Предусмотрены Suspense/loading, пустая выдача, неверные фильтры, 404 и error boundary. Навигация и таблица адаптируются к узкому экрану; таблица прокручивается горизонтально.

## Ограничения и развитие

Нет разграничения доступа, многопользовательского редактирования, UI импорта, обновления импортированных объектов и управляемого назначения текущих оценок. Для конкурентного изменения бизнес-иерархии нужна отдельная политика сериализации: текущий trigger защищает последовательные изменения, но не заменяет такую политику. Нет производственных гарантий и полного аудита изменений. Эти функции не требуются техническому фундаменту.

Для больших визуализаций следует добавлять специализированные агрегаты; каталог не будет отдавать все сценарии в браузер. Проверка 2 500 записей относится к подготовке данных и серверной пагинации, а не к производительности будущего радара.
