- Выполняйте только согласованную задачу; сохраняйте принятые интерфейсы, API, фильтры, URL-состояние, сортировку и инспектор вне её области.
- Начинайте с `git status --short`, `git diff` и целевого `rg`. Читайте связанные файлы, а не весь проект и историю отчётов. Не переустанавливайте зависимости без необходимости.
- Карта: `src/app` — маршруты/API; `src/features` — сценарные интерфейсы; `src/domain` — контракты; `src/server` и `src/db` — сервисы/БД; `tests/browser` — Playwright.
- Команды и состав проверок сверяйте с `package.json`, `playwright.config.ts` и `.github/workflows/ci.yml`; старые отчёты не заменяют текущую конфигурацию.
- Переиспользуйте dev-сервер (`npm run dev`, порт 3000), проверив репозиторий, порт и БД. Не останавливайте чужие процессы. Сборку для dev-проверок не запускайте.

### 1. Во время разработки

- Выбирайте проверки по изменению: `npx eslint <изменённые-файлы>`, `npm run typecheck`, `npm test -- tests/filter-state.test.ts` (пример; подставьте связанный тест).
- Браузер запускайте при изменении поведения или отображения: нужный spec, при необходимости `--grep`, сначала `--project=1440`; для адаптивности добавьте затронутые размеры.
- Пример PowerShell для уже работающего dev-сервера: `$env:PLAYWRIGHT_BASE_URL='http://127.0.0.1:3000'; npm run test:e2e -- tests/browser/catalog-33.spec.ts --project=1440`. После проверки восстановите прежнее значение переменной (удалите, если её не было).
- При изменении общих компонентов обязательно проверяйте зависимые экраны. Для общих фильтров, URL, навигации, инспектора и стилей расширяйте проверки на связанные представления.
- Успешные проверки повторяйте после новых влияющих изменений или при нерешённой проблеме. Снимки сохраняйте по задаче, трассы разбирайте при сбое; не выводите полные логи успешных прогонов.

### 2. Перед завершением обычной задачи

- На готовом изменении выполните один `npm run check` (lint, типы, Vitest, production build); браузерные проверки в него не входят.
- Выполните релевантные браузерные проверки на необходимых разрешениях и просмотрите итоговый diff и результаты. Не запускайте весь E2E-набор и тесты на 2500 сценариях без оснований из уровня 3; полный набор не требуется перед каждой фиксацией кода.
- После сборки используйте свежий production-сервер: `npm start -- --port 3002` (перезапустите свой старый сервер), убрав dev-переопределение `PLAYWRIGHT_BASE_URL`.

### 3. Полная регрессия

- Выполняйте перед релизом, слиянием крупных изменений или после правок общих механизмов. Полный набор обязателен при высоком риске регрессий: изменениях общей CSS-системы, схемы данных, фильтрации, URL-состояния, навигации или общей логики визуализаций.
- Выполните `npm run check`, если он ещё не прошёл на текущем состоянии кода.
- Перед `npm run test:postgres` явно проверьте наличие `TEST_DATABASE_URL` и убедитесь, что она указывает на отдельную тестовую базу с суффиксом `_test` в имени. Если условие не выполнено, не запускайте команду. Тест пересоздаёт схемы и готовит набор 2500 сценариев.
- Для обычной браузерной регрессии используйте отдельную синтетическую БД с 80 сценариями. Seed не уменьшает набор 2500 до 80; не смешивайте эти базы.
- На свежем production-сервере из уровня 2 выполните `npm run test:e2e` — все spec на всех согласованных разрешениях (сейчас четыре размера в конфигурации).
- На том же production-сервере выполните HTTP-проверки: в PowerShell `$env:BASE_URL='http://127.0.0.1:3002'; npm run test:http`, затем восстановите прежнее значение переменной.
- Для набора 2500 выполните `node scripts/verify-large.mjs` после PostgreSQL-тестов; порт 3003 должен быть свободен, чтобы Playwright запустил сервер с нужной тестовой БД.
- Просмотрите итоговый diff и результаты. После отправки изменений любого уровня проверьте CI того же коммита. CI запускает выбранные spec и не заменяет полный локальный прогон, когда требуется уровень 3.
- Для изменений только документации достаточно просмотра diff; учитывайте явные ограничения пользователя на запуск проверок. В отчёте различайте выполненные и пропущенные проверки.
