# Передача разработки ЦТВ

Состояние на 9 ноября 2026 года. Исходная рабочая версия — `6fd4fae8c0f98b51cb4117c8d2852c9dbae3d26e` из ветки `codex/free-beta` проекта `mihajlovfeda3/ctv-platform`. История этой версии сохранена в передаваемом репозитории. Текущая ветка независимой копии — `main`.

## Ответственность и границы

Разработчики работают в этом отдельном репозитории и собственных локальных БД. Render, облачная БД и публикация общей ссылки остаются только у исходного владельца. Здесь нет подключения к его развёртыванию, облачных паролей или права менять его сервисы. Push в эту копию не обновляет общую ссылку. Для принятия работ владелец отдельно переносит проверенные изменения.

Запуск описан в `README.md`, постоянный процесс проверок — в `AGENTS.md`. Ассистенту сначала прочитать эти файлы и `CLAUDE.md`. Полная переписка для запуска не требуется.

Основной запуск — Node.js 24 и обычный локальный PostgreSQL 17, без Docker.
Разработчик создаёт отдельную пустую БД и задаёт свои локальные настройки в
`.env`. Docker оставлен дополнительным вариантом. `setup-handoff.mjs`
генерирует только настройки этого дополнительного варианта.

## Что реализовано

- Обзор платформы.
- Сценарии: каталог, технологический 2D-радар, матрица зрелости, 3D-куб; общие фильтры, URL-контекст и выбор сценария.
- Быстрый просмотр и полная карточка сценария. Описание разворачивается, технический ID в быстром просмотре скрыт, в полной карточке находится во второстепенной информации.
- Куб: камера/zoom/reset, компактные подписи направлений, фокус, пространственные ориентиры РЗ/ОГ, синхронизированная развёртка РЗ × ОГ, тёмный инспектор, полный экран и fallback без WebGL.
- «Бизнес и задачи»: бизнес-ландшафт, классы задач, матрица функций × технологий, карточка класса с переходами к сценариям.
- Серверные API чтения сценариев, импорт CSV/JSON через CLI, синтетический генератор, миграции и тесты.
- «Технологии и рынок» и «Внутренний портфель» сохраняют существующий ограниченный объём реализации; их не считать полноценными аналитическими разделами.

## Принятые контракты

1. Статусы сценария: только `yes` — «Реализуется» (синий), `no` — «Не реализуется» (оранжевый). Не возвращать пользовательский статус «Неизвестно» и не превращать отсутствие сведений в `no`.
2. РЗ — 1–5; ОГ — 1–7; влияние — 1–3. Пропуск оценки остаётся пропуском. Контекст текущих демонстрационных оценок — `synthetic-lab`.
3. Восемь технологических направлений задаются действующей классификацией. Организационные блоки, функциональные группы и процессы — разные справочники. Наследуемые имена в коде не являются основанием менять семантику данных.
4. Бизнес-ландшафт: подтверждённая функциональная группа из `scenario_functional_groups` → фактический процесс сценария. Конфликт/отсутствие классификации показывается явно. Виртуальные узлы представления не являются новыми записями БД.
5. Матрица покрытия считает уникальные связанные сценарии в пересечении функции и технологии, отдельно — `yes`. Сценарий с несколькими технологиями может входить в несколько ячеек. Общие итоги считаются по уникальным ID, не суммой ячеек. Фильтр реализации матрицы относится к сценариям.
6. Доля классов задач с реализуемыми сценариями — характеристика имеющихся связей. Она не означает долю решённых задач или цифровизацию компании. Для отраслевого сравнения зон роста/успеха данных недостаточно.
7. Демо-классы и их связи основаны на повторяющихся профилях генератора. Равномерность не является доказательством корпоративной методологии. Не создавать новые связи ради заполнения диаграмм.
8. Геометрия куба принята: `cubeDistance(РЗ) = 0.28 + (5 − РЗ) × 0.2`; ОГ меняет угол на фиксированном конусе при сохранении расстояния до вершины. Камера не меняет координаты данных. Сценарии с неполными оценками учитываются отдельно. Геометрию и шкалы не переписывать без самостоятельного задания.

## Данные комплекта

`handoff/database-snapshot.json` — точный снимок 26 таблиц прикладной схемы с 80 синтетическими сценариями. ID, связи, оценки, точность временных меток и признаки происхождения сохранены. `handoff/manifest.json` содержит SHA-256 файла и контрольные суммы таблиц. Это данные приложения, а не файлы локальной или облачной PostgreSQL.

`node scripts/restore-handoff.mjs` применяет миграции и вставляет снимок одной транзакцией с проверкой всех таблиц. Скрипт разрешает только loopback-подключение к отдельной БД с окончанием `_handoff` или `_handoff_test`, отказывается перезаписывать существующие строки и откатывает вставку при несовпадении контрольной суммы. Не запускать seed до/после восстановления для получения исходного состояния. Для повторного старта используйте новую пустую БД; удаление существующей БД не автоматизировано.

Снимок может содержать содержательные поля сценариев. В передаваемом наборе сценарии синтетические; реальные корпоративные PDF/XLSX, материалы вне Git и полная переписка не включены. Для дальнейшего наполнения используйте согласованные источники; не восстанавливайте отсутствующие факты по догадкам.

## Проверки и продолжение

- Перед правками: `git status --short`, целевые чтения, затем связанная проверка по `AGENTS.md`.
- Для восстановления: `node scripts/restore-handoff.mjs --verify-only`.
- Для новой логики восстановления: `npm test -- tests/handoff-restore.test.ts`.
- На готовом коде один `npm run check`. Для UI — соответствующие Playwright spec, без бессмысленного повторения полного набора.
- PostgreSQL-тесты, которые пересоздают схемы, допустимы только с отдельной `TEST_DATABASE_URL` на БД с суффиксом `_test`. Нельзя подставлять рабочую БД.
- Начните с собственной ветки. После согласования задачи меняйте только её область. Не переносите код в другой фреймворк, не переустанавливайте зависимости и не переделывайте принятые экраны без необходимости.
- После изменений бизнес/сценарных выборок проверяйте дедупликацию, отсутствующие оценки и применимые URL-переходы.

Передаваемый baseline ранее прошёл CI и 11 целевых браузерных проверок опубликованной версии. Результаты проверки именно этого комплекта см. в `handoff/VERIFICATION.md`; результаты baseline не заменяют проверку новой задачи.
